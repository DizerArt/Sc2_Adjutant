## Быстрый запуск: три шага

1. Откройте PowerShell в `D:\dev\Sc2_Adjutant\02_application` и выполните
   `npm run review:compose`. Дождитесь окна приложения. Сохраните напечатанные
   launcher-ом путь отдельного профиля и каталог evidence. Это настоящие
   WebView2, IPC и SQLite с тестовыми данными; SC2 и внешние источники отключены.
2. В другом PowerShell из той же папки выполните `npm run review:browser`.
   Откройте напечатанный адрес контрольной страницы и ссылки приложения/OBS.
   Здесь настоящий собранный React UI, но IPC и состояния SC2 — фикстуры.
   Порт назначается системой; адрес8766 из рабочего приложения не подставляйте.
3. Проходите строки ниже: сначала N в native-окне, затем B/S на браузерном
   стенде. Для каждого результата запишите ID, фактическое поведение и evidence.
   Для ошибки достаточно ID + «ожидалось/получилось» + снимок экрана.

Команды предназначены для подготовленного окружения разработки; они не являются
установщиком зависимостей. Нет Docker, скачивания моделей, изменения сцен OBS
или запуска обработки видео. Сборка может занимать несколько минут.

Повторный native-запуск с тем же профилем нужен для проверки сохранения:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/review-compose.ps1 -NoBuild -Profile '<путь профиля из первого запуска>'
```

`-PrepareOnly` готовит сборку/стенд без открытия окна; `-NoBuild` использует
имеющуюся сборку. Не применяйте `-NoBuild` после изменения исходников, пока
сборка не обновлена. `-Profile` должен указывать на профиль этого review-стенда,
а не на рабочие данные Electron/Tauri или исходного Python-приложения.

Параметры launcher-а передавайте прямо PowerShell-скрипту, как выше: npm в
некоторых PowerShell-окружениях поглощает аргументы после `--`. Для подготовки
без запуска используйте ту же команду с `-PrepareOnly` и без `-Profile`.
Папка реплеев закреплена за `fixtures/replays` этого профиля; её смена на рабочую
папку отклоняется. Наблюдение и синхронизация читают только тестовую папку.

## Что именно подтверждает каждый стенд

| Стенд | Подтверждает | Не подтверждает |
|---|---|---|
| N — `review:compose` | Реальный EXE/WebView2, native IPC, SQLite, тестовый импорт, системные окна/трэй | Живой SC2, настоящий матч/реплей, качество синтеза без модели, установку NSIS |
| B/S — `review:browser` | Реальную вёрстку и взаимодействия собранного UI, контролируемые состояния/ошибки | Rust-валидацию, SQLite, native-диалог, реальные IPC/SC2/OBS; ответы bridge здесь подменены |
| M — отдельная ручная проверка | Только фактически выполненное действие в реальных SC2/OBS/чистой Windows | Всё, что не было явно проверено и записано |

Контрольная страница меняет только тестовые фикстуры. Она не должна появляться
в production-источнике OBS. Синтетический успешный ответ, снимок браузера или
прохождение unit-теста не отмечаются как успешный native/OBS сценарий.

Браузерный launcher печатает `CONTROL_URL`, `APP_URL` (`/app/`), `OBS_URL`
(`/widgets/`). В control UI доступны фазы menu/loading/game/pause/unknown,
активность карточки, ошибки normal/stale/malformed/disconnect/image404/ipc-error/
source-unavailable и результат следующего выбора: synthetic PNG, bundled GIF,
cancel, error. Это управляемый ответ fake bridge, не окно выбора файла Windows.
Введите ID строки, статус и заметку в контрольной странице, чтобы сохранить
результат. Если для сценария нет готового переключателя, зафиксируйте BLOCKED
и недостающее управление; не используйте production-профиль как обходной путь.

## Evidence и свежесть

Для одного прохода используйте один каталог под `02_application/.compose-test-data/`,
например `.compose-test-data/visual-review-2026-10-26/` относительно `02_application`.
Автоматические артефакты launcher-а оставляйте в напечатанном им каталоге;
в журнале укажите ссылку на него. Пользовательские картинки/БД не копируйте в
evidence. Используйте только синтетические материалы.

Браузерный стенд сохраняет
`.compose-test-data/visual-browser-<UUID>/{session.json,state.json,results.json,events.ndjson}`:
метаданные запуска, состояние фикстуры, введённые результаты и журнал действий.
`results.json` с введённым PASS — запись проверяющего, а не автоматическое
доказательство; приложите скриншоты и фактическое описание. Native-профиль и
его метаданные берите из вывода native launcher-а.

В `results.md` запишите время, команды/параметры, путь запущенного EXE, профиль,
адреса стенда, размер окна/viewport, масштаб Windows, язык и reduced-motion.
Приложите build stamp/manifest, если launcher его создаёт; иначе укажите время
сборки и SHA256 EXE/основного JS. Номер1.1.11 сам по себе не отличает сборки.
После пересборки старые скриншоты не считаются доказательством нового состояния.

Имена снимков: `<ID>-<шаг>-<RU|EN>-<размер>.png`. Для анимаций нужен короткий
видеофрагмент либо два снимка с интервалом и описание наблюдения. Скриншот
сам по себе не доказывает SQLite-персистентность, отмену или освобождение порта.
Статусы: `NOT RUN`, `PASS`, `FAIL`, `BLOCKED`, `N/A` с причиной. Не проставляйте
PASS целой группе по одному удачному экрану.

## Что пока не принимать как готовую функцию

Полная замена TS/Node-парсера Rust-кодом не завершена. Единый каталог виджетов,
раскладки/анимированная миграция между экранами, перенос старых профилей/паков,
универсальная калибровка и manual cover остаются отдельными этапами. Четыре
постматчевых вида потерь ещё не интегрированы. Шортсы **PAUSED**, готовая вкладка
автоматического создания/синхронизации видео не заявляется. Отсутствие этих
функций — известный scope, а не результат успешного тестирования.
