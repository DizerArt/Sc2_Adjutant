# Compose: объединение SC2 Adjutant и StarCraft Adjutant

Требование28.10: карта потерь использует все доступные editor exports по точной
версии карты, иначе извлекает миникарту из соответствующего локального .s2ma.
Без экспорта и локального архива сохраняется схема с честным статусом.
Ресурсы поставляются с приложением; абсолютные пути исходного проекта не нужны.
Привязка camera bounds приблизительная до отдельной проверки контрольных точек.

Дополнение26.10: просмотр послематчевых виджетов включает командные игры и FFA.
Прямой выбор replay не зависит от истории1×1, не меняет её статистику. Сохраняются
реальные команды/владельцы. Не обещать произвольный arcade/co-op без tracker facts;
автоматический импорт многопользовательской истории требует отдельной модели.

Решение26.10: меню допускает все4постматчевых вида одновременно. Сетка32столбца
по X и64строки по Y; целые координаты/размеры внутри полотна. Рамки перемещаются
и меняют размер на месте, доступны клавиатура/числовые поля. Независимые включатели,
пресет2×2, черновик/Apply. Общие факты/время одного матча; никаких демоданных в
production. Точная карта и паритет анализа требуют проверки реальными реплеями.

Дата решения: 25.10.2026. Рабочая ветка: `compose`.
Основание: явное поручение владельца; локальная работа без публикации.
Ветка создана от текущей `side-logic-integration`, исходная точка `9187ff4`.

## Результат продукта

Одно локальное Windows-приложение с ядром Rust, оболочкой Tauri 2 и React/TypeScript.
Функции обоих проектов сохраняются; частичная замена оболочки не считается полной
миграцией. Реальные ограничения данных и разбора не скрываются нулями или успехом.

## Этап 1 — миграция приложения друга (текущий)

До объединения виджетов перенести действующий SC2 Adjutant с проверкой паритета:

- Определение соперника/матча 1×1, мониторинг и восстановление подключения SC2.
- Профили по расам, barcode/идентичность, BattleTag, MMR/лига, кандидаты SC2Pulse,
  заметки, маркеры, теги и статистика встреч.
- История, фильтры, избранное, подробности, графики и порядок строительства.
- Синхронизация/наблюдение реплеев, привязка к матчу, повторный импорт без дублей.
- Диагностика, настройки, RU/EN, управление окном/компактным режимом, действующая
  плавающая карточка и её позиционирование.
- Локальная озвучка Piper и корректная диагностика отсутствующих моделей.
- Импорт CSV/XML/JSON без изменения оригиналов; неизвестные поля, заметки,
  raceProfiles и внешние ссылки не теряются. Перед миграцией — проверяемая копия;
  ошибки импорта не превращаются в пустую базу. Исходный Electron остаётся fallback.
- Реальная сборка Windows, установщик и запуск на изолированных данных.

Целевой стек: Tauri 2, Rust stable MSVC, Cargo workspace, React/TypeScript/Vite/npm,
Tokio, Serde, SQLite/rusqlite, Axum для OBS, reqwest/WebSocket и FFmpeg/FFprobe.
Блокирующие операции отделены от UI. Папки ресурсов/профиля/кэша разделены.

Разрешён временный совместимый адаптер существующего парсера/предметной логики,
если он нужен для сохранения поведения. Он явно маркируется как переходный долг;
его наличие НЕ позволяет объявить полный перенос ядра на Rust завершённым.
Встроенный WebView не отменяет необходимость проверки настоящего Tauri IPC.

Критерий выхода: все перечисленные функции подтверждены, данные сравниваются
до/после на копии, исходники сохранены, сборка и запуск воспроизводимы. Пробелы
паритета перечисляются в STATUS, а не маскируются демонстрационными ответами.

## Этап 2 — единый умный оверлей

Уточнение пользователя25.10.2026: основной способ показа стримовых виджетов —
HTML-страница через локальный URL и OBS Browser Source. Текущее прозрачное окно
карточки не является окончательным OBS-интерфейсом. Оно может остаться отдельным
необязательным режимом для игрока; браузерный источник показывает оформление
в трансляции и сам по себе не накладывает его поверх игры на экране игрока.
Динамическая страница обслуживается Rust-сервером, а не открывается как file://.

По умолчанию один общий Browser Source на размер полотна: общий слой рендерит
выбранные виджеты и перемещает тот же ID между раскладками. Отдельные URL виджетов
допустимы как дополнительная возможность, но не заменяют общий слой с переходами.
Редактирование раскладки находится в приложении, OBS получает готовое отображение.
Постоянный loopback URL и работа при закрытом окне настроек — требования реализации,
а не утверждение о готовности текущего Tauri-прототипа.

Действующая карточка соперника включается в общую систему виджетов вместе с нашим
умным оверлеем. Один профиль содержит каталог виджетов и раскладки по экранам.
Под экраном пока понимается режим стрима: меню, загрузка, игра/реплей, пауза,
постматч. Физический монитор/выход — отдельная настройка, если понадобится.

- Пользователь выбирает видимость, позицию, размер и порядок слоёв виджета
  отдельно для каждого режима; координаты нормализованы к размеру полотна.
- Один и тот же виджет имеет постоянный ID/данные и разные размещения в режимах.
- Предпросмотр/черновик отделены от явно применённой рабочей версии.
- Переход между режимами может плавно перемещать/масштабировать общий виджет.
  Прерывание перехода использует текущую позицию, а не создаёт дубликат.
- Reduced motion и мгновенный переход доступны. Скрытие чувствительной области
  при загрузке имеет приоритет: подложка не ждёт декоративной анимации.
- Browser Source OBS остаётся локальным URL с устойчивым портом/путём; закрытие
  окна настроек не выключает стрим. Несколько клиентов не владеют состоянием.
- Не создавать и не менять пользовательские OBS-сцены без отдельного действия.

## Этап 3 — постматч как часть умного оверлея

Существующие четыре представления потерь — fountain, battle_map, armies, heroes —
становятся виджетами/вариантами общей системы. Пользователь может выбрать несколько
вариантов и их размещение. Одновременное размещение и последовательный показ
описываются отдельными настройками, без повторного анализа одного реплея.
Единые данные матча, участники/цвета, шкала времени, запуск, повтор и длительность.
Отсутствующие цены/фон/точные позиции обозначаются явно; схема не выдаётся за карту.

## Этап 4 — шортсы (PAUSED)

Создание шортсов в дальнейшем находится в отдельной вкладке. Минимум ручных
настроек, автоматизация синхронизации и подготовки, максимум ответственности за
результат на приложении. Текущий сложный процесс не переносится как утверждённый UX.
Существующие проекты, оригиналы, результаты и внутренние контракты сохраняются.
Разработка интерфейса/алгоритмов шортсов возобновляется после отдельного
проектирования с пользователем. Сейчас не добавлять рабочую вкладку-заглушку,
не запускать обработку и не менять настройки ради демонстрации.

## Полнота интеграции нашего проекта

До признания объединения завершённым составить проверенный реестр всех функций
StarCraft Adjutant: проекты/материалы, импорт и версии разбора, очередь/отмена,
видео/реплеи, таймлайн/синхронизация, калибровка/геометрия, цены/потери, карты,
шаблоны/свои изображения/профили, OBS и необязательные адаптеры. Каждому элементу
назначить статус «перенесён», «переходный адаптер», «на паузе» или «не готов».
Нельзя считать объединением только перенос страницы оверлея.

## Границы и проверки

Оригиналы записей/реплеев read-only. Локальные секреты не переносятся в исходники,
экспорт или логи. Сетевые источники отключаемы; локальная работа без них проверяется.
Тесты используют временные данные и fake SC2; реальный SC2/OBS не трогают.
Команды процессов — массивы аргументов с таймаутом/отменой и проверкой владельца.
Тесты паритета Rust↔TS, импорта/ошибок/повторного запуска, браузерные проверки,
реальный Tauri smoke и отдельная проверка установки/переноса. Лицензии и ресурсы
проверяются до распространения. Коммиты/push/публикация отдельно не поручались.
